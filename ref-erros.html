SQL Erros Comuns

Todo mundo erra SQL, todo dia: uma letra trocada no nome da tabela, uma vírgula sobrando, aspas do tipo errado. O SQLite sempre avisa, mas avisa em inglês e com poucas palavras. Esta página é um dicionário dessas mensagens: cada uma aparece exatamente como sai no editor do guia e no terminal do sqlite3, com a tradução, a causa mais comum, o conserto e a aula onde o assunto é explicado.

Como usar esta página
  • Deu erro? Copie o começo da mensagem (por exemplo, no such column) e procure nesta página com Ctrl+F.
  • As mensagens foram colhidas no SQLite 3.50.4: no editor do guia e no terminal da Ana (ana@notebook), com o banco da Loja Aurora. Nenhuma foi escrita de memória.
  • Os quadros "Resultado" desta página rodam o SQL errado de verdade no seu navegador: a mensagem em vermelho é a que o seu SQLite deu agora.

Como ler uma mensagem de erro

O mesmo erro aparece um pouco diferente em cada lugar. No editor do guia, a mensagem sai crua, do jeito que o SQLite a escreveu:

SELECT nomee FROM clientes;

No terminal do SQLite, o programa sqlite3 acrescenta um prefixo e, muitas vezes, uma seta mostrando onde ele se perdeu:

$ sqlite3 loja.db
SQLite version 3.50.4 2025-07-30 19:33:53
Enter ".help" for usage hints.
sqlite> SELECT nomee FROM clientes;
Parse error: no such column: nomee
  SELECT nomee FROM clientes;
         ^--- error here
Parse error:
"Erro de análise". O SQLite nem começou a rodar: o problema foi achado ao ler o comando (nome que não existe, sintaxe errada). Nada no banco mudou.
no such column: nomee
A mensagem em si: "não existe a coluna nomee". É o mesmo texto que o editor mostra.
SELECT nomee FROM clientes;
O terminal repete o seu comando…
^--- error here
…e aponta o lugar do erro ("o erro está aqui"). Quando o ponto fica no fim da linha, a seta vira error here ---^, com o ^ à direita.

Um erro para tudo

Quando um comando dá erro, ele inteiro é cancelado: um INSERT de várias linhas que falha na terceira não grava nem a primeira. No editor, a execução também para no comando com erro; os comandos de baixo não rodam.

1. Nomes que não existem

O grupo mais comum de todos: o SQLite não achou a tabela, a coluna ou a função com o nome que você escreveu. Quase sempre é uma letra trocada, um plural esquecido ou um apelido mal usado. Os nomes das tabelas do guia estão todos no plural: clientes, produtos, pedidos, itens_pedido…

Aspas duplas no texto

Este é o erro de quem vem do Excel ou de outra linguagem de programação, onde texto vai entre aspas duplas:

SELECT nome, email
FROM clientes
WHERE nome = "Ana Carvalho Lima";

O SQLite leu "Ana Carvalho Lima" como o nome de uma coluna e não achou coluna nenhuma com esse nome. A própria mensagem dá a dica: should this be a string literal in single-quotes?, "isto não deveria ser um texto entre aspas simples?". No terminal, a seta aponta para as aspas:

sqlite> SELECT nome FROM clientes WHERE nome = "Ana Carvalho Lima";
Parse error: no such column: "Ana Carvalho Lima" - should this be a string literal in single-quotes?
  SELECT nome FROM clientes WHERE nome = "Ana Carvalho Lima";
                           error here ---^

Atenção: o editor do guia e o terminal da Ana usam um SQLite configurado como o padrão do SQL manda (a opção DQS=0). Muitos programas antigos usam um SQLite "tolerante", que, quando não acha a coluna, aceita o texto entre aspas duplas sem reclamar. Não conte com isso: além de fora do padrão, se um dia existir uma coluna com aquele nome, a consulta passa a comparar com a coluna, sem erro nenhum. Use sempre aspas simples para texto.

O comando que não termina, no terminal

No editor, um parêntese aberto sem ; dá incomplete input. No prompt do sqlite3, ninguém reclama: o terminal acha que você ainda vai continuar o comando e muda o prompt para ...> (continuação). Se houver um parêntese aberto, o prompt mostra quantos: (x1...>.

sqlite> SELECT nome FROM clientes WHERE (id = 1
(x1...> ;
Parse error: near ";": syntax error
  SELECT nome FROM clientes WHERE (id = 1 ;
                            error here ---^

Quando o ; finalmente chega, o SQLite vê o parêntese que não fechou e reclama. Se o terminal "travou" mostrando ...>, quase sempre falta um ; (ou uma aspa, ou um parêntese): digite o que falta e Enter. Já com o SQL na linha de comando, a mensagem é a mesma do editor:

$ sqlite3 loja.db "SELECT nome FROM clientes WHERE (id = 1"
Error: in prepare, incomplete input
$ sqlite3 loja.db "SELECT nome FROM clientes WHERE nome = 'Ana"
Error: in prepare, unrecognized token: "'Ana"
  SELECT nome FROM clientes WHERE nome = 'Ana
                           error here ---^

Missão: esta consulta tem dois erros. Rode, leia a mensagem, conserte, rode de novo e leia a próxima mensagem. No fim, ela deve mostrar o nome e o email da cliente Ana Carvalho Lima.

SELECT nome, email
FROM cliente
WHERE nome = "Ana Carvalho Lima";

SELECT nome, email
FROM clientes
WHERE nome = 'Ana Carvalho Lima';

sqlite> INSERT INTO pedidos (cliente_id, funcionario_id, data, frete) VALUES (999, 2, '2026-10-18', 0);

sqlite> INSERT INTO clientes (id, nome) VALUES ('abc', 'Teste');

A chave estrangeira que não reclama

Repare no PRAGMA foreign_keys = ON; antes do pedido do cliente 999. No programa sqlite3, a checagem de chave estrangeira vem desligada e precisa ser ligada a cada vez que você abre o banco:

sqlite> PRAGMA foreign_keys;
0

Com 0 (desligada), aquele INSERT do cliente 999 passa sem erro nenhum, e o banco fica com um pedido de um cliente que não existe. No editor do guia, a Loja Aurora já é carregada com a checagem ligada. Mais em FOREIGN KEY e em PRAGMAs.

Missão: a Ana quer criar a categoria "Pet Shop", mas o INSERT dá UNIQUE constraint failed. Conserte para que a categoria nova entre (a tabela deve ficar com 9 categorias). Dica: quem precisa escolher o id?

INSERT INTO categorias (id, nome, descricao)
VALUES (1, 'Pet Shop', 'Ração e brinquedos para bichos');

INSERT INTO categorias (nome, descricao)
VALUES ('Pet Shop', 'Ração e brinquedos para bichos');

E no editor do guia?

O editor tem dois limites próprios. Um comando de ponto vira near ".": syntax error (tabela da seção 2). E um SQL que nunca termina, como uma CTE recursiva sem LIMIT, é interrompido depois de uns 4 segundos com a mensagem interrupted ("interrompido"). No terminal, o mesmo SQL ficaria rodando até você apertar Ctrl+C.

O %s e o %d são os lugares onde o banco põe o nome da tabela, da coluna ou o número da linha. Uma diferença importante: no PostgreSQL, dividir por zero é erro (22012 division_by_zero), e as aspas duplas são sempre nome, nunca texto, como no editor do guia.

Exercícios

1. A Ana rodou SELECT nome FROM produto; e recebeu no such table: produto. O que aconteceu?

2. Qual mensagem o SQLite dá para WHERE cidade = "Teresina"?

3. misuse of aggregate function COUNT() apareceu numa consulta com WHERE COUNT(*) > 2. Qual é o conserto?

4. No terminal, depois de Enter, o prompt virou ...> e nada aconteceu. O que falta, provavelmente?

5. SELECT COUNT(*) FROM clientes WHERE email = NULL; mostrou 0, mas há clientes sem email. Por quê?

6. Traduza a mensagem

Complete: UNIQUE constraint failed: clientes.id quer dizer que o valor da coluna id já na tabela.

Resumo

  • No editor, a mensagem sai crua (no such table: cliente). No terminal, vem com prefixo: Parse error (o comando nem rodou), Runtime error … (19) (parou no meio), ou Error: in prepare / Error: stepping com o SQL na linha de comando.
  • no such table, no such column, ambiguous column name: confira o nome (as tabelas do guia estão no plural) e, num JOIN, diga de qual tabela é a coluna.
  • near "X": syntax error: o erro está em X ou logo antes dele. Vírgula sobrando, palavra errada, partes fora de ordem.
  • Texto vai entre aspas simples. Aspas duplas são para nomes, e dão no such column: "…".
  • … constraint failed: o comando estava certo, os dados quebraram uma regra da tabela (UNIQUE, NOT NULL, FOREIGN KEY, CHECK). No sqlite3, a chave estrangeira só é checada com PRAGMA foreign_keys = ON.
  • Agregada no WHERE dá misuse of aggregate: filtre grupos com HAVING.
  • Cuidado com o que não dá erro: = NULL, 7/2, 1/0, 'abc' + 1 e o UPDATE sem WHERE.
