SQL Modelando um Banco do Zero

Até aqui você usou o banco da Loja Aurora, que já veio pronto. Mas alguém teve de decidir que existiriam as tabelas clientes, pedidos e itens_pedido, e quais colunas cada uma teria. Esse trabalho se chama modelagem. Nesta aula você acompanha a Ana modelando, do zero, o banco da clínica veterinária da prima dela, que hoje anota tudo num caderno. São sete passos, sempre os mesmos, que servem para qualquer banco: uma escola, uma biblioteca, as suas finanças.

Você vai aprender
  • Por que "uma planilha só" vira problema, com um exemplo real.
  • Achar as entidades (as coisas que viram tabelas) e os atributos (as colunas).
  • Escolher a chave primária de cada tabela.
  • Ligar as tabelas: relacionamentos 1 para N, e em que lado vai a chave estrangeira.
  • Transformar as regras do negócio em NOT NULL, CHECK, UNIQUE e REFERENCES.
  • Escrever os CREATE TABLE, pôr dados de teste e conferir se o banco responde às perguntas do dia a dia.
  • As mensagens reais de erro, e a armadilha das chaves estrangeiras desligadas no terminal.

Os exemplos rodam de verdade no seu navegador, no SQLite 3.50. O banco da clínica não existe no editor: cada exemplo cria as tabelas e põe os dados antes de consultar, porque cada Rodar parte do banco limpo (aula O Editor do Guia). Os nomes, telefones e registros da clínica são todos inventados.

A ideia: do caderno às fichas

Na recepção da clínica tem um caderno. Cada consulta marcada vira uma linha:

06/10 09:00  Rex (cachorro, nasc. 10/04/2019) — João Pereira, (86) 90000-0001 — Dr. Paulo — vacina antirrábica — R$ 80
06/10 10:30  Mingau (gato) — Ana Lima, (86) 90000-0002 — Dra. Lúcia — check-up anual — R$ 120
13/10 14:00  Rex (cachorro) — João Pereira, (86) 90000-0001 — Dra. Lúcia — dor na pata — R$ 150
20/10 08:30  Pipoca (ave) — Rita Sales, (86) 90000-0003 — Dr. Paulo — corte de unhas — R$ 40
20/10 09:00  Thor (cachorro, nasc. 22/01/2023) — João Pereira, (86) 90000-0001 — Dr. Paulo — vacina V10 — R$ 90

Repare: o telefone do João está escrito três vezes. O Rex aparece duas. Cada linha mistura quatro assuntos: quando foi a consulta, qual animal, de quem ele é e quem atendeu. Modelar é separar esses assuntos em fichas diferentes (uma pasta de fichas de tutores, uma de animais, uma de veterinários, uma de consultas) e ligar as fichas pelo número de cada uma. Cada pasta vira uma tabela.

A primeira ideia de quem sai do caderno é copiar o caderno numa tabela só, com uma coluna para cada pedaço da linha:

-- o João trocou de telefone; a recepcionista corrigiu só a consulta de hoje
UPDATE caderno SET telefone = '(86) 90000-0009'
WHERE tutor = 'João Pereira' AND data_hora LIKE '2026-10-20%';

SELECT DISTINCT tutor, telefone FROM caderno ORDER BY tutor;

Agora o banco diz que o João tem dois telefones, e ninguém sabe qual é o certo. Isso acontece porque a mesma informação (o telefone do João) está guardada em várias linhas. E há outros problemas escondidos:

  • Para cadastrar um animal novo, que ainda não teve consulta, não há onde: toda linha é uma consulta.
  • Se a consulta da Pipoca for desmarcada e apagada, a clínica perde o telefone da Rita, que só estava ali.
  • Nada impede alguém de escrever "cachoro" ou "Joao Pereira", e aí o "mesmo" tutor vira dois.

Esses defeitos têm nome e regra para evitar, e são o assunto da aula Normalização. Aqui, a solução vem pelos passos.

Passo 1: as coisas (entidades)

Leia o caderno e sublinhe os substantivos, as "coisas" de que a clínica precisa lembrar. Cada coisa que tem vida própria (existe e tem dados mesmo sem as outras) é uma entidade, e cada entidade vira uma tabela:

CoisaTem vida própria?Vira
Tutor (o dono do animal)Sim: tem nome e telefone, mesmo sem consulta marcadatabela tutores
AnimalSim: tem nome, espécie, nascimentotabela animais
VeterinárioSim: tem nome e registro profissionaltabela veterinarios
ConsultaSim: um acontecimento, com data, motivo e valortabela consultas
Telefone, espécie, valor…Não: são detalhes de uma das coisas acimacolunas (passo 2)

Um truque para não errar: se você consegue dizer "um tutor", "dois animais", "cinco consultas", é uma entidade. Ninguém diz "dois telefones do caderno" como coisa separada; é o telefone de alguém.

Passo 2: os detalhes (atributos)

Para cada entidade, a Ana pergunta à prima: "o que você precisa saber sobre um tutor? E sobre um animal?". Cada resposta é um atributo, que vira uma coluna:

TabelaColunas
tutoresnome, telefone, email
animaisnome, espécie, nascimento
veterinariosnome, CRMV (o registro no conselho de veterinária)
consultasdata e hora, motivo, valor

Três cuidados nesta hora:

  • Um valor por coluna. Nada de uma coluna "telefones" com '(86) 90000-0001, (86) 90000-0005': você não conseguiria buscar por um deles. Se o tutor pode ter vários telefones, telefone vira uma tabela própria.
  • Não guarde o que se calcula. A idade do animal muda todo ano; guarde o nascimento e calcule a idade na consulta (aula Funções de Data).
  • Cada detalhe na tabela da coisa a que ele pertence. O telefone é do tutor, não da consulta. Por isso ele fica em tutores, uma vez só.

Passo 3: a chave de cada tabela

Cada linha precisa de um jeito único e que nunca muda de ser apontada: a chave primária (aula PRIMARY KEY). Qual coluna usar?

CandidataServe?Por quê
O nome do tutorNãoPode haver dois "João Pereira"; e se ele corrigir a grafia, todas as ligações quebram
O telefoneNãoMuda (o João acabou de mudar o dele)
O CRMV do veterinárioQuaseÉ único, mas é um texto comprido para repetir em cada consulta, e tem gente que ainda não tem
Um número inventado: id INTEGER PRIMARY KEYSimÚnico, curto, nunca muda e o SQLite gera sozinho (aula AUTOINCREMENT)

A Ana segue o mesmo padrão da Loja Aurora: toda tabela começa com id INTEGER PRIMARY KEY. O CRMV continua guardado, como coluna UNIQUE (passo 5): único, mas não é ele que liga as tabelas.

Passo 4: as ligações (relacionamentos)

Agora, como as fichas se ligam. Para cada par de entidades, faça a mesma pergunta nos dois sentidos:

PerguntaRespostaTipo
Um tutor tem quantos animais? E um animal tem quantos tutores?Um tutor, vários animais (o João tem o Rex e o Thor). Um animal, um tutor.1 para N
Um animal tem quantas consultas? E uma consulta é de quantos animais?Um animal, várias consultas. Uma consulta, um animal.1 para N
Um veterinário faz quantas consultas? E uma consulta é feita por quantos?Um veterinário, várias. Uma consulta, um veterinário.1 para N

A regra do 1 para N (lê-se "um para ene", ou "um para muitos") é sempre a mesma: a chave estrangeira vai no lado do N, o lado "dos muitos". Cada animal guarda o tutor_id do seu tutor; cada consulta guarda o animal_id e o veterinario_id. É como em cada ficha de animal escrever "tutor: ficha nº 1".

tutores (1) ──────< (N) animais (1) ──────< (N) consultas (N) >────── (1) veterinarios
   id                  id                       id                         id
   nome                tutor_id → tutores       animal_id → animais        nome
   telefone            nome                     veterinario_id → veterin.  crmv
   email               especie                  data_hora
                       nascimento               motivo
                                                valor

O < na ponta da linha marca o lado "dos muitos". Esse desenho, com as tabelas e as ligações, é um diagrama do banco, e tem um jeito padrão de desenhar, com o "pé de galinha" no lado N: é a aula Diagramas (DER).

E se os dois lados forem "vários"?

Se uma consulta pudesse ter vários veterinários (uma cirurgia com dois), e cada veterinário várias consultas, seria uma relação N para N. Aí a chave estrangeira não cabe em nenhum dos dois lados, e entra uma terceira tabela, de ligação, como a itens_pedido da Loja Aurora, que liga pedidos e produtos. Esse caso tem aula própria: Relação Muitos-para-Muitos. Na clínica da prima da Ana, por enquanto, cada consulta tem um veterinário só.

Passo 5: as regras

Cada frase da prima do tipo "tem de", "não pode" ou "só pode" vira uma regra que o próprio banco garante. Assim, um erro de digitação é barrado na entrada, e não descoberto meses depois:

A prima disse…No banco
"Todo tutor tem de deixar um telefone."telefone TEXT NOT NULL (aula NOT NULL)
"Email, só se a pessoa quiser."email TEXT, sem NOT NULL: aceita NULL
"Atendemos cachorro, gato e ave; o resto é 'outro'."CHECK (especie IN ('cachorro', 'gato', 'ave', 'outro')) (aula CHECK)
"Não existem dois veterinários com o mesmo CRMV."crmv TEXT NOT NULL UNIQUE (aula UNIQUE)
"Todo animal tem um tutor cadastrado."tutor_id INTEGER NOT NULL REFERENCES tutores(id) (aula FOREIGN KEY)
"Valor de consulta não pode ser negativo."CHECK (valor >= 0)

Passo 6: os CREATE TABLE

Com tudo decidido, escrever as tabelas é quase copiar os passos. A ordem importa: uma tabela só pode apontar para outra que já existe, então primeiro as que não dependem de ninguém (tutores, veterinarios), depois animais, por último consultas.

CREATE TABLE tutores (
  id       INTEGER PRIMARY KEY,
  nome     TEXT NOT NULL,
  telefone TEXT NOT NULL,
  email    TEXT
);

CREATE TABLE veterinarios (
  id    INTEGER PRIMARY KEY,
  nome  TEXT NOT NULL,
  crmv  TEXT NOT NULL UNIQUE
);

CREATE TABLE animais (
  id         INTEGER PRIMARY KEY,
  tutor_id   INTEGER NOT NULL REFERENCES tutores(id),
  nome       TEXT NOT NULL,
  especie    TEXT NOT NULL CHECK (especie IN ('cachorro', 'gato', 'ave', 'outro')),
  nascimento TEXT
);

CREATE TABLE consultas (
  id             INTEGER PRIMARY KEY,
  animal_id      INTEGER NOT NULL REFERENCES animais(id),
  veterinario_id INTEGER NOT NULL REFERENCES veterinarios(id),
  data_hora      TEXT NOT NULL,
  motivo         TEXT NOT NULL,
  valor          REAL NOT NULL CHECK (valor >= 0)
);

SELECT name FROM sqlite_schema WHERE type = 'table' AND name IN ('tutores', 'veterinarios', 'animais', 'consultas');
nomes no plural e em minúsculas
tutores, animais: uma tabela guarda vários. Sem acento e sem espaço (veterinarios, não veterinários), para não precisar de aspas em todo comando.
id INTEGER PRIMARY KEY
A chave do passo 3, sempre a primeira coluna.
tutor_id, animal_id, veterinario_id
As chaves estrangeiras do passo 4, com o nome da tabela apontada no singular mais _id. Quem lê animal_id sabe na hora para onde ela aponta.
data_hora TEXT
O SQLite não tem um tipo de data: datas vão como texto no formato '2026-10-20 09:00', que se ordena certo e funciona com as funções de data (aula Datas e Horas).
NOT NULL, CHECK, UNIQUE, REFERENCES
As regras do passo 5.
SELECT name FROM sqlite_schema …
Confere que as quatro tabelas foram criadas. A sqlite_schema é a tabela onde o SQLite guarda a lista de tudo o que existe no banco.

-- 1. Qual é a agenda do dia 20/10?
SELECT c.data_hora, a.nome AS animal, t.nome AS tutor, t.telefone, v.nome AS veterinario, c.motivo
FROM consultas c
JOIN animais a      ON a.id = c.animal_id
JOIN tutores t      ON t.id = a.tutor_id
JOIN veterinarios v ON v.id = c.veterinario_id
WHERE c.data_hora >= '2026-10-20' AND c.data_hora < '2026-10-21'
ORDER BY c.data_hora;

-- 2. Qual é o histórico do Rex?
SELECT c.data_hora, c.motivo, v.nome AS veterinario, c.valor
FROM consultas c
JOIN veterinarios v ON v.id = c.veterinario_id
WHERE c.animal_id = 1
ORDER BY c.data_hora;

-- 3. Quanto cada tutor já gastou?
SELECT t.nome, COUNT(c.id) AS consultas, SUM(c.valor) AS total
FROM tutores t
JOIN animais a        ON a.tutor_id = t.id
LEFT JOIN consultas c ON c.animal_id = a.id
GROUP BY t.id
ORDER BY total DESC;

Formas diferentes de fazer a mesma coisa

Modelar é escolher. Algumas escolhas que aparecem em todo projeto:

DecisãoOpção AOpção BO que a Ana escolheu, e por quê
Chave primáriaUm número inventado (id), a chamada chave substitutaUm dado do mundo real (CPF, CRMV), a chave naturalid: nunca muda e é curto. O dado real fica numa coluna UNIQUE
Data e horaUma coluna data_hora: '2026-10-20 09:00'Duas colunas, data e horaUma só: ordena e compara faixas com um só WHERE
DinheiroREAL (80.0)INTEGER em centavos (8000)REAL, como na Aurora. Em sistemas com muitas contas, centavos inteiros evitam as "caudas" de ponto flutuante (aula Funções Numéricas)
EspécieTexto com CHECK (… IN …)Uma tabela especies e um especie_idCHECK: são quatro valores que quase nunca mudam. Se a lista crescer muito ou ganhar detalhes, vira tabela
Nomestutores, tutor_idTutor, TutorIDMinúsculas com _, como no resto do guia. O importante é escolher um padrão e seguir em todas as tabelas

O que aconteceu: no SQLite, a verificação das chaves estrangeiras vem desligada (PRAGMA foreign_keys respondeu 0), por compatibilidade com bancos antigos. O REFERENCES estava no modelo, mas ninguém conferia, e a consulta do animal 99 entrou. O PRAGMA foreign_key_check acusou o problema depois do fato: a linha 6 de consultas aponta para um animal que não existe. Com PRAGMA foreign_keys = ON, o erro aparece na hora (o (19) é o número do erro no SQLite).

Como consertar: rode PRAGMA foreign_keys = ON; toda vez que abrir o banco (no terminal ou no programa). Ele vale só para aquela conexão, não fica gravado no arquivo. No editor do guia ele já vem ligado, por isso o erro apareceu no exemplo anterior. Mais em PRAGMAs Úteis.

Nos outros bancos

Os passos da modelagem são os mesmos em qualquer banco. O que muda são os tipos e a forma de gerar o id. O trecho é ilustrativo (PostgreSQL) e não roda no SQLite:

-- PostgreSQL (ilustrativo)
CREATE TABLE consultas (
  id             INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  animal_id      INTEGER NOT NULL REFERENCES animais(id),
  veterinario_id INTEGER NOT NULL REFERENCES veterinarios(id),
  data_hora      TIMESTAMP NOT NULL,
  motivo         VARCHAR(200) NOT NULL,
  valor          NUMERIC(10, 2) NOT NULL CHECK (valor >= 0)
);
  • Datas ganham tipos próprios (DATE, TIMESTAMP), e dinheiro, um tipo decimal exato (NUMERIC/DECIMAL). Veja Tipos de Dados.
  • O id automático se escreve GENERATED … AS IDENTITY ou SERIAL no PostgreSQL, AUTO_INCREMENT no MySQL e IDENTITY no SQL Server.
  • Nesses bancos, as chaves estrangeiras são conferidas sem precisar de um PRAGMA.

Resumo

  • Modelar é separar os assuntos misturados num caderno ou numa planilha em tabelas ligadas entre si. Uma tabela só repete dados, e dados repetidos acabam discordando.
  • Entidades (coisas que se contam: tutor, animal, consulta) viram tabelas; atributos (detalhes de cada coisa) viram colunas, um valor por coluna, sem guardar o que se calcula.
  • Cada tabela ganha id INTEGER PRIMARY KEY; dados reais únicos (CRMV, CPF) ficam como UNIQUE.
  • Em 1 para N, a chave estrangeira vai no lado N (animais.tutor_id). Em N para N, entra uma tabela de ligação.
  • As regras do negócio viram NOT NULL, CHECK, UNIQUE e REFERENCES. No terminal do SQLite, ligue PRAGMA foreign_keys = ON.
  • Crie primeiro as tabelas que não dependem de ninguém, ponha dados de teste e confira se o modelo responde às perguntas reais.
