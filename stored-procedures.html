Stored Procedures

Uma stored procedure ("procedimento guardado") é um bloco de comandos SQL que fica salvo dentro do banco, com um nome, pronto para ser chamado quando você quiser — como uma receita guardada na gaveta, em vez de ditar os passos toda vez. Os bancos com servidor (MySQL, PostgreSQL, SQL Server) têm esse recurso. O SQLite, por ser um banco embutido num arquivo, não tem — e nesta aula você vai ver como os outros bancos criam uma procedure, por que o SQLite faz diferente e qual é o recurso dele que mais se parece: o TRIGGER, que você vai rodar de verdade no editor.

Você vai aprender
  • O que é uma stored procedure e para que serve.
  • Como MySQL, PostgreSQL e SQL Server criam (CREATE PROCEDURE) e chamam (CALL / EXEC).
  • Por que o SQLite não tem procedures (a lógica fica na linguagem do programa).
  • O recurso mais próximo no SQLite: o TRIGGER, um mini-procedimento que dispara sozinho.
  • Como um TRIGGER registra mudanças e como ele pode barrar uma operação ruim.

Os comandos CREATE PROCEDURE, CALL e EXEC são ilustrativos (não existem no SQLite, não rodam no editor) e vêm da documentação oficial de cada banco. Os TRIGGER do fim rodam de verdade, no editor, contra a Loja Aurora.

A ideia: a receita guardada

Imagine que, toda sexta, a Ana faz o mesmo cálculo: somar as vendas da semana, tirar a média e guardar num relatório. Ela pode reescrever todos os comandos toda vez — fácil errar — ou escrever uma vez, dar um nome (fechar_semana) e, nas próximas, só dizer "rode o fechar_semana". Esse "bloco com nome, guardado no banco" é a stored procedure. As vantagens:

  • Não repetir um SQL comprido em vários lugares do programa.
  • Padronizar: todo mundo chama a mesma procedure e faz a conta do mesmo jeito.
  • Às vezes, desempenho: o banco já tem o plano pronto.

1. Criar e chamar (bancos com servidor)

A procedure tem um nome, pode receber parâmetros e tem um corpo (os comandos). Depois, você a chama pelo nome. Veja em cada banco, como na documentação oficial.

MySQL

DELIMITER //

CREATE PROCEDURE contar_clientes (IN uf CHAR(2), OUT quantos INT)
BEGIN
  SELECT COUNT(*) INTO quantos FROM clientes WHERE estado = uf;
END//

DELIMITER ;

CALL contar_clientes('PI', @quantos);
SELECT @quantos;
CREATE PROCEDURE contar_clientes (…)
"Criar procedimento" com esse nome e seus parâmetros.
IN uf CHAR(2)
Um parâmetro de entrada (IN): o valor que você passa. Há também OUT (saída) e INOUT.
BEGIN … END
O corpo: os comandos que a procedure roda.
DELIMITER //
Um truque do cliente mysql: como o corpo tem ; dentro, troca-se o fim de comando para // enquanto se cria a procedure, e depois volta para ;. A própria documentação explica isso.
CALL contar_clientes('PI', @quantos)
"Chamar": roda a procedure passando PI e recebendo a contagem na variável @quantos.

PostgreSQL

CREATE PROCEDURE inserir_categoria(nome TEXT, descricao TEXT)
LANGUAGE SQL
BEGIN ATOMIC
  INSERT INTO categorias (nome, descricao) VALUES (nome, descricao);
END;

CALL inserir_categoria('Pet Shop', 'Produtos para animais');

No PostgreSQL também se chama com CALL. Repare que ele pede a linguagem do corpo (LANGUAGE SQL, entre outras).

SQL Server

CREATE PROC contar_clientes @uf CHAR(2)
AS
SELECT COUNT(*) AS quantos FROM clientes WHERE estado = @uf;

Chamada com EXEC: EXEC contar_clientes 'PI';. No SQL Server os parâmetros começam com @ (como mostra a documentação, @ID INT) e se chama com EXECUTE (abreviado EXEC).

Procedure × função

Você também vai ouvir falar em função guardada (CREATE FUNCTION). A diferença prática: uma função devolve um valor e entra no meio de um SELECT (como COUNT()); uma procedure é um bloco que você chama à parte com CALL/EXEC e que pode fazer várias coisas. Os dois ficam guardados no banco.

2. Por que o SQLite não tem procedures

É a mesma razão dos usuários e permissões: o SQLite é um banco embutido. Ele não fica ligado como um servidor; ele roda dentro do seu programa. Então o lugar natural para guardar "um bloco de passos com um nome" não é o banco — é a linguagem do programa. Onde outro banco teria uma procedure, um programa com SQLite tem uma função comum na sua linguagem (aula SQL nas Linguagens).

Veja a "procedure" contar_clientes escrita como uma função Python — é onde a lógica mora no mundo SQLite:

import sqlite3
con = sqlite3.connect("loja.db")

def contar_clientes(uf):                 # a "procedure" vira uma função
    sql = "SELECT COUNT(*) FROM clientes WHERE estado = ?"
    return con.execute(sql, (uf,)).fetchone()[0]

print(contar_clientes("PI"))             # a "chamada"

Essa escolha mantém o SQLite pequeno e previsível. O que o banco não guarda, o programa guarda — e fica mais fácil de testar e versionar junto com o resto do código.

3. O recurso mais próximo: o TRIGGER

Há um pedaço de "procedure" que o SQLite tem: o TRIGGER ("gatilho"). Um trigger é um bloco de SQL, guardado no banco, que dispara sozinho quando acontece um INSERT, UPDATE ou DELETE numa tabela. Você não o chama; ele reage. É como uma procedure que o banco executa automaticamente na hora certa. (Há uma aula sobre eles no roteiro; aqui vemos o essencial para comparar com as procedures.)

Um trigger que registra mudanças de preço

Suponha que a Ana queira guardar um histórico toda vez que o preço de um produto muda. Ela cria uma tabela de log e um trigger que, depois de cada mudança de preco, grava o antes e o depois:

CREATE TABLE precos_log (
  produto_id   INTEGER,
  preco_antigo REAL,
  preco_novo   REAL
);

CREATE TRIGGER registrar_mudanca_preco
AFTER UPDATE OF preco ON produtos
BEGIN
  INSERT INTO precos_log (produto_id, preco_antigo, preco_novo)
  VALUES (OLD.id, OLD.preco, NEW.preco);
END;

UPDATE produtos SET preco = 1.49 WHERE id = 1;
UPDATE produtos SET preco = 3.20 WHERE id = 2;

SELECT * FROM precos_log;
AFTER UPDATE OF preco ON produtos
Quando disparar: depois de um UPDATE da coluna preco na tabela produtos.
BEGIN … END
O corpo do trigger, igual ao corpo de uma procedure: o que ele faz quando dispara.
OLD.preco e NEW.preco
Dentro do trigger, OLD é a linha antes da mudança e NEW é depois. Aqui ele grava os dois no log.

Repare que você só deu dois UPDATE; o INSERT no log aconteceu sozinho, duas vezes, por conta do trigger. Isso é a cara de uma procedure que roda na hora certa, sem ninguém chamar.

Um trigger que barra uma operação ruim

Triggers também servem para proteger os dados. Este dispara antes de um UPDATE de preço e, se o novo preço for negativo, cancela tudo com uma mensagem — usando a função RAISE ("levantar [um erro]"):

CREATE TRIGGER preco_nao_negativo
BEFORE UPDATE OF preco ON produtos
WHEN NEW.preco < 0
BEGIN
  SELECT RAISE(ABORT, 'preço não pode ser negativo');
END;

UPDATE produtos SET preco = -5 WHERE id = 1;
BEFORE UPDATE OF preco
Dispara antes da mudança, a tempo de impedi-la.
WHEN NEW.preco < 0
Uma condição: o corpo só roda se o novo preço for negativo.
RAISE(ABORT, '…')
Cancela a operação (ABORT) e devolve a mensagem. O UPDATE não acontece.

A mensagem preço não pode ser negativo é a que o próprio trigger definiu: o SQLite a repassa como erro. A regra "preço nunca é negativo" passou a viver dentro do banco, valendo para qualquer programa que o use — exatamente o tipo de coisa que, num banco com servidor, você poria numa procedure ou numa trigger procedure.

E as views?

O outro recurso do SQLite que lembra "lógica guardada no banco" é a view (aula Views): uma consulta salva com um nome, que você usa como se fosse uma tabela. Ela não executa ações como uma procedure, mas guarda, com um nome, um SELECT que você reaproveita — a mesma ideia de "não repetir" das procedures. Você viu uma em Usuários e Permissões.

Quando dá errado

Tentar CREATE PROCEDURE no SQLite

Como não existe no SQLite, escrever CREATE PROCEDURE no editor dá erro de sintaxe já na palavra PROCEDURE:

CREATE PROCEDURE contar() BEGIN SELECT 1; END;

A mensagem near "PROCEDURE": syntax error ("erro de sintaxe perto de PROCEDURE") confirma: o motor não conhece esse comando. Para "um bloco com nome", use uma função na sua linguagem (seção 2) ou, para algo que dispara sozinho, um TRIGGER (seção 3).

Resumo

  • Uma stored procedure é um bloco de SQL guardado no banco, com nome, que você chama quando quer. Serve para não repetir e para padronizar.
  • Bancos com servidor criam com CREATE PROCEDURE e chamam com CALL (MySQL, PostgreSQL) ou EXEC (SQL Server).
  • O SQLite não tem procedures: é embutido, e a lógica fica numa função da linguagem do programa (aula SQL nas Linguagens).
  • Dentro do banco, o recurso mais próximo é o TRIGGER: um bloco que dispara sozinho em INSERT/UPDATE/DELETE, com OLD/NEW e RAISE — bom para registrar mudanças e barrar operações ruins. A view guarda uma consulta com nome.
