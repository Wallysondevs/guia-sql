Projeto: Biblioteca

Aos sábados, a Ana é voluntária na biblioteca comunitária do bairro, em Teresina. Os empréstimos são anotados num caderno: quem levou, que livro, em que dia. Para saber quem está atrasado, alguém folheia o caderno inteiro e conta os dias no calendário. Neste projeto você troca o caderno por um banco de dados, construído em versões: começa com uma tabela só, descobre por que ela não basta, separa os autores, registra sócios e empréstimos e, no fim, o banco calcula sozinho os atrasos, as multas e os livros que estão na estante.

Você vai aprender
  • A começar simples (uma tabela) e a perceber quando é hora de dividir.
  • Por que o nome do autor vai para uma tabela própria, ligada por chave estrangeira.
  • A registrar empréstimos com data de retirada e de devolução, e a achar os que estão em aberto com IS NULL.
  • A calcular dias, prazos e multas com julianday e date.
  • A contar exemplares disponíveis com LEFT JOIN, e a armadilha do filtro no lugar errado.
  • A proteger o banco com CHECK e UNIQUE, e a emprestar e devolver com INSERT e UPDATE.

Como as caixas deste projeto funcionam

A biblioteca é um banco novo, que não tem nada a ver com a Loja Aurora. Só que o editor do guia, a cada Rodar, cria um banco limpo e carrega a Aurora; ele não lembra o que você criou no Rodar anterior. Por isso o SQL de cada caixa faz tudo, do começo:

  1. Monta a biblioteca: CREATE TABLE e INSERT das tabelas daquela versão.
  2. Consulta: o SELECT que responde à pergunta da versão.

A montagem se repete de caixa em caixa, sempre igual à da versão anterior, mais a novidade. As tabelas da Aurora continuam lá, mas os nomes não se misturam: a biblioteca usa livros, autores, socios e emprestimos, que a Aurora não tem. Fora do editor, num arquivo de verdade, você montaria uma vez só (veja o projeto a Loja Aurora Completa, no fim).

Versão 1: uma tabela só, igual ao caderno

O jeito mais rápido de começar é copiar o caderno: uma tabela de livros, com o título, o autor e o ano.

    id     INTEGER PRIMARY KEY,
    titulo TEXT NOT NULL,
    autor  TEXT,
    ano    INTEGER
);

INSERT INTO livros (titulo, autor, ano) VALUES

('Memórias Póstumas de Brás Cubas', 'Machado de assis', 1881),
('Iracema',                         'José de Alencar',  1865),
('O Guarani',                       'José de Alencar',  1857);

SELECT * FROM livros;

Todo livro tem título (aula NOT NULL).
autor TEXT
O nome do autor, digitado em cada livro, como no caderno.

O ano da primeira edição: um número inteiro, que dá para comparar e ordenar.

Versão 2: os autores ganham uma tabela

A coordenadora da biblioteca pergunta: "quantos livros temos de cada autor?". Um GROUP BY responde (aula GROUP BY), e entrega o problema:

CREATE TABLE livros (id INTEGER PRIMARY KEY, titulo TEXT NOT NULL, autor TEXT, ano INTEGER);
INSERT INTO livros (titulo, autor, ano) VALUES
('Dom Casmurro',                    'Machado de Assis', 1899),
('Memórias Póstumas de Brás Cubas', 'Machado de assis', 1881),
('Iracema',                         'José de Alencar',  1865),
('O Guarani',                       'José de Alencar',  1857);

SELECT autor, COUNT(*) AS livros
FROM livros
GROUP BY autor;

Para o banco, Machado de Assis e Machado de assis são textos diferentes, e o Machado virou dois autores com um livro cada. Com o nome digitado em cada livro, todo erro de digitação cria um autor "novo", e corrigir exige achar cada cópia. A saída é a mesma que a Loja Aurora usa para as categorias: o autor vira uma tabela própria, com o nome escrito uma vez só, e o livro guarda apenas o número dele (aulas Tabelas que se Relacionam e Normalização).

Versão 3: sócios e empréstimos

O caderno da biblioteca, na verdade, é uma lista de empréstimos: "a Helena levou Dom Casmurro no dia 1º, devolveu no dia 10". Cada empréstimo liga um livro a um sócio, com duas datas. A data de devolução fica vazia (NULL) enquanto o livro não volta (aula O Valor NULL).

A tabela "do meio": cada linha liga um livro a um sócio. Um livro tem muitos empréstimos ao longo do tempo e um sócio faz muitos: é uma relação muitos-para-muitos com informação própria, as datas (aula Relação Muitos-para-Muitos).
retirada TEXT NOT NULL
Todo empréstimo tem data de saída, no formato AAAA-MM-DD, o que as funções de data entendem (aula Datas e Horas).
devolucao TEXT
Sem NOT NULL: vazia quer dizer "o livro ainda está com o sócio".
dois JOINs
O empréstimo sabe os números; os JOINs trazem o nome do sócio e o título.

Versão 4: prazos, atrasos e multas

A regra da biblioteca: o prazo é de 14 dias e cada dia de atraso custa R$ 0,50. Para contar dias entre duas datas, o SQLite tem a função julianday: ela transforma uma data num número de dias, e a diferença entre dois desses números é a distância em dias (aula Funções de Data).

Um detalhe: para o resultado desta página não mudar a cada dia, o "hoje" do projeto é fixo, 18 de outubro de 2026, escrito como '2026-10-18'. Num sistema de verdade, no lugar dele vai date('now'), a data do dia.

A data de retirada mais 14 dias: o último dia do prazo. A Helena levou O Cortiço em 20/09 e devia ter devolvido até 04/10.
julianday('2026-10-18') - julianday(e.retirada)
Quantos dias se passaram desde a retirada. O resultado vem com casa decimal (28.0), porque o julianday também conta horas.
CAST(… AS INTEGER)
Converte para inteiro: 28 (aula Os Tipos no SQLite).

A Helena está com O Cortiço há 28 dias, e o Jonas com Memórias Póstumas há 17. Os dois passaram dos 14. O atraso é "dias menos 14", mas só quando isso dá positivo; para quem está dentro do prazo, o atraso é zero. O MAX com dois valores devolve o maior deles, e resolve: MAX(dias - 14, 0).

Versão 6: regras que o banco garante

Até aqui, o banco aceita qualquer coisa que a voluntária digitar. Duas regras evitariam os erros mais comuns do caderno:

  1. Autor repetido com outra caixa de letra, como o "Machado de assis" da versão 1. Um UNIQUE proíbe nome repetido (aula UNIQUE), e o COLLATE NOCASE faz o SQLite comparar sem ligar para maiúsculas e minúsculas.

Data num formato que o julianday não entende

Como consertar: guarde sempre as datas em AAAA-MM-DD. Nos outros bancos

O julianday é do SQLite. Nos bancos com tipo DATE de verdade, contar dias é mais direto. Trechos ilustrativos, que não rodam no editor:

-- PostgreSQL: subtrair duas datas dá o número de dias
SELECT DATE '2026-10-18' - DATE '2026-09-20';           -- 28
-- MySQL / MariaDB
SELECT DATEDIFF('2026-10-18', '2026-09-20');             -- 28
-- SQL Server
SELECT DATEDIFF(day, '2026-09-20', '2026-10-18');        -- 28

Repare que a ordem dos argumentos do DATEDIFF é invertida entre o MySQL e o SQL Server. O COLLATE NOCASE também é do SQLite; nos outros bancos, comparar sem diferenciar maiúsculas depende da collation da coluna. Mais em As Diferenças entre os Bancos.

Resumo

  • Comece simples, com uma tabela, e divida quando aparecer repetição: o autor digitado em cada livro virou uma tabela autores, ligada por autor_id.
  • Um empréstimo é a tabela do meio entre livros e sócios, com as datas. devolucao vazia (NULL) quer dizer "ainda está com o sócio".
  • julianday(b) - julianday(a) conta dias; date(a, '+14 days') soma dias; MAX(x, 0) impede atraso negativo. Datas sempre em AAAA-MM-DD, senão as funções devolvem NULL.
  • Para contar "inclusive quem não tem par", LEFT JOIN + COUNT(coluna). Condição sobre a tabela da direita vai no ON; no WHERE, ela some com linhas sem avisar.
  • UNIQUE COLLATE NOCASE e CHECK fazem o banco recusar os erros do caderno.
  • No dia a dia, emprestar é INSERT e devolver é UPDATE … WHERE id = ….
