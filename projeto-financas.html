Projeto: Controle de Gastos

Todo mês acontece a mesma coisa com a Ana: o salário cai no dia 1º e, lá pelo dia 25, ela não sabe para onde foi o dinheiro. Ela já tentou caderno, planilha e aplicativo. Agora vai tentar o que aprendeu neste guia: um banco de dados só dela, com cada gasto anotado e o SQL respondendo às perguntas. Quanto gastei no mercado? Estourei o orçamento do lazer? Quanto sobrou em setembro? Neste projeto você constrói esse banco em versões e, no caminho, aprende a regra de ouro de quem guarda dinheiro em banco de dados: nada de casas decimais "soltas".

Você vai aprender
  • A começar com uma tabela de gastos e a somar por categoria.
  • Por que REAL engana com dinheiro (0.1 + 0.2 não é 0.3) e como guardar tudo em centavos.
  • A registrar entradas e saídas na mesma tabela, pelo sinal do valor, e a mostrar reais com printf.
  • A criar categorias com um orçamento mensal e comparar com o que foi gasto.
  • Entradas, saídas e saldo por mês com CASE dentro do SUM.
  • O saldo acumulado, dia a dia, com SUM() OVER.
Como as caixas deste projeto funcionam

O controle de gastos é um banco novo. Como o editor começa do zero a cada Rodar (com a Loja Aurora carregada), toda caixa traz a montagem (as tabelas e os lançamentos) e, depois do comentário -- a consulta, a pergunta daquela versão. A montagem só muda quando a versão muda o modelo.

Versão 2: dinheiro em centavos

Antes de crescer o banco, um teste que todo programador faz uma vez na vida e nunca esquece:

SELECT 0.1 + 0.2       AS soma,
       0.1 + 0.2 = 0.3 AS igual,
       0.1 + 0.2 - 0.3 AS diferenca,
       10 + 20 = 30    AS igual_em_centavos;

A soma aparece como 0.3, mas a comparação com 0.3 dá 0, falso. A diferença mostra o porquê: sobra um 5.55111512312578e-17 (0,0000000000000000555…). O tipo REAL guarda números em binário, e 0.1 em binário é uma dízima, como 1/3 em decimal: o computador guarda uma aproximação. Na tela, o arredondamento esconde o erro; na comparação, ele aparece (aula Os Tipos no SQLite).

E isso acontece com os dados da Ana. O total do mercado em setembro "é" 890.95, mas:

SELECT 385.90 + 92.35 + 412.70          AS total_mercado,
       385.90 + 92.35 + 412.70 = 890.95 AS bate_com_890_95;

Não bate. Num relatório que só mostra o número, ninguém percebe; num WHERE total = 890.95, a linha some. A solução clássica é guardar o dinheiro em centavos, como número inteiro: 385.90 vira 38590. Inteiros são exatos: somam, subtraem e comparam sem resto nenhum. E já que vamos refazer a tabela, ela passa a guardar também as entradas, como o extrato do banco: dinheiro que entra é positivo, dinheiro que sai é negativo.

Centavos, inteiros. O salário de R$ 3.500,00 é 350000; o supermercado de R$ 385,90 é -38590.
o sinal

valor / 100.0
Volta para reais só na hora de mostrar. O .0 é obrigatório: valor / 100, com dois inteiros, faria divisão inteira e jogaria os centavos fora (38590 / 100 dá 385).
printf('%.2f', …)
Formata com exatamente 2 casas: 385.90, -60.00… O %.2f quer dizer "número com 2 casas decimais" (aula Funções de Texto).

CREATE TABLE categorias (
    id     INTEGER PRIMARY KEY,

"A tabela categorias já existe": é a das categorias de produto da Loja Aurora, que o editor carrega. Num banco só da Ana não haveria conflito, mas o nome categorias_gasto é até melhor: diz de quê são as categorias.

       SUM(CASE WHEN valor > 0 THEN valor ELSE 0 END) / 100.0  AS entradas,

       SUM(valor) / 100.0 AS saldo

GROUP BY mes;

Soma só os negativos, com o sinal trocado, para a coluna "saídas" sair positiva.

Quando dá errado

Comparou um REAL com = 
CREATE TABLE gastos (descricao TEXT, categoria TEXT, valor REAL);
INSERT INTO gastos VALUES ('Supermercado', 'Mercado', 385.90),
                          ('Feira', 'Mercado', 92.35),
                          ('Supermercado', 'Mercado', 412.70);

SELECT categoria, SUM(valor) AS total
FROM gastos
GROUP BY categoria
HAVING SUM(valor) = 890.95;

O que aconteceu: nenhuma linha. O total "é" 890.95 na tela, mas não é exatamente 890.95 na memória, e o = compara bit a bit. Sem erro, sem aviso.

Como consertar: guarde centavos em INTEGER (versão 2). Se precisar lidar com um REAL que já existe, compare arredondado: HAVING ROUND(SUM(valor), 2) = 890.95.

Dividiu por 100 e perdeu os centavos 
SELECT 38590 / 100   AS inteira,
       38590 / 100.0 AS com_ponto,
       printf('%.2f', 38590 / 100.0) AS formatada;

O que aconteceu: 38590 / 100 deu 385. Inteiro dividido por inteiro, no SQLite, é divisão inteira: os 90 centavos foram embora, sem aviso.

Como consertar: divida por 100.0. Basta um dos lados ter ponto para a conta ter casas decimais.

Esqueceu o sinal do gasto 
CREATE TABLE lancamentos (descricao TEXT, valor INTEGER NOT NULL);
INSERT INTO lancamentos VALUES ('Salário', 350000),
                               ('Aluguel', 110000);   -- faltou o sinal de menos

SELECT SUM(valor) / 100.0 AS saldo FROM lancamentos;

O que aconteceu: saldo de 4600.0, em vez de 2400.0. O aluguel entrou como se fosse dinheiro recebido. Na convenção do sinal, esquecer o - é o erro mais comum, e o banco não tem como saber.

Como consertar: corrija com UPDATE lancamentos SET valor = -110000 WHERE descricao = 'Aluguel';. Para não depender do sinal, existe outra forma de modelar: valor sempre positivo, com CHECK (valor > 0), e uma coluna tipo com CHECK (tipo IN ('entrada', 'saida')). O saldo vira SUM(CASE WHEN tipo = 'entrada' THEN valor ELSE -valor END): mais longo, mas o banco recusa um tipo errado (aula CHECK).

Dividiu por um limite que não existe 
SELECT 100 / 0             AS por_zero,
       100 / NULL          AS por_null,
       ROUND(100.0 * 350000 / NULL, 1) AS salario_usado;

O que aconteceu: as três dão NULL, e nenhuma dá erro. No SQLite, dividir por zero devolve NULL. Por isso a categoria Salário, com limite NULL, não quebraria a versão 6; ela ficaria com usado vazio (e lá ela nem aparece, porque o WHERE l.valor < 0 tira as entradas).

Como consertar: decida o que mostrar: COALESCE(…, 'sem limite') troca o NULL por um texto (aula IFNULL e COALESCE). E não conte com esse comportamento nos outros bancos (veja abaixo).

Nos outros bancos

Os bancos com servidor têm um tipo decimal exato para dinheiro: DECIMAL(10,2) ou NUMERIC(10,2) (PostgreSQL, MySQL, SQL Server). Lá, 385.90 + 92.35 + 412.70 = 890.95 é verdadeiro, e guardar em centavos é opcional. O SQLite aceita escrever DECIMAL(10,2) no CREATE TABLE, mas guarda o valor como REAL do mesmo jeito: o nome do tipo não muda a matemática (aula Os Tipos no SQLite).

Divisão por zero também muda: o PostgreSQL e o SQL Server param com erro (division by zero); o MySQL, no modo padrão, devolve NULL com um aviso, como o SQLite. E o printf é do SQLite; para formatar números, o PostgreSQL usa to_char, o MySQL FORMAT e o SQL Server FORMAT. Mais em As Diferenças entre os Bancos.

Saldo (convenção do sinal)SUM(valor)

Por mêsstrftime('%Y-%m', data) AS mes … GROUP BY mes

Saldo acumuladoSUM(valor) OVER (ORDER BY data, id)

-- a consulta
WITH ranking AS (
    SELECT strftime('%Y-%m', data) AS mes, descricao, -valor / 100.0 AS gasto,
           RANK() OVER (PARTITION BY strftime('%Y-%m', data) ORDER BY valor) AS posicao
    FROM lancamentos
    WHERE valor < 0
)
SELECT mes, descricao, gasto
FROM ranking
WHERE posicao = 1;

Resumo

  • Dinheiro no SQLite vai em INTEGER, em centavos. REAL guarda aproximações: 0.1 + 0.2 = 0.3 é falso, e um total "890.95" pode não ser 890.95.
  • Calcule em centavos e divida por 100.0 (com ponto) só para mostrar; printf('%.2f', …) garante as duas casas.
  • Com entradas positivas e saídas negativas, o saldo é SUM(valor); CASE dentro do SUM separa entradas e saídas.
  • Categorias com limite numa tabela própria permitem comparar gasto e orçamento com GROUP BY mes, c.id e HAVING.
  • SUM() OVER (ORDER BY …) dá o saldo acumulado; com PARTITION BY, ele recomeça a cada mês.
  • No SQLite, dividir inteiros corta a parte decimal e dividir por zero dá NULL, sem erro. Comece porcentagens por 100.0 *.
