Projeto: da Planilha ao Banco

A Norte Suprimentos, fornecedora da Loja Aurora, mandou por email a planilha dos produtos que vai começar a vender: oito linhas, salvas como CSV. A Marta quer os produtos cadastrados no banco até o fim do dia. Digitar um por um? Nem pensar. Neste projeto a Ana leva a planilha do arquivo até a tabela produtos, no terminal do sqlite3: importa, descobre que veio tudo bagunçado, limpa com SQL, converte os tipos, insere e, no fim, exporta um CSV de volta para conferência. É o trabalho mais comum do mundo com bancos de dados, e quase nunca dá certo de primeira.

Você vai aprender
  • O que é um arquivo CSV e como criá-lo e conferi-lo no terminal.
  • A importar com .import --csv, e por que tudo chega como texto.
  • A limpar os problemas de toda planilha: espaços sobrando, vírgula decimal, células vazias, linhas repetidas, nomes que não batem.
  • A converter os tipos com CAST, REPLACE, TRIM e NULLIF.
  • A levar os dados limpos para a tabela de verdade com INSERT INTO … SELECT.
  • A exportar de volta para CSV com .headers, .mode csv e .once.

Este projeto acontece em dois lugares. A importação e a exportação são comandos de ponto do programa sqlite3 (aula Comandos de Ponto), que só existem no terminal: os quadros pretos mostram a sessão real da Ana, no computador dela. A limpeza é SQL puro, e essa você pratica no editor do guia, em cada versão. A aula Importar e Exportar CSV explica os comandos em detalhe; aqui eles trabalham juntos num caso real.

A ideia: CSV é uma planilha em texto puro

CSV quer dizer comma-separated values, "valores separados por vírgula". É uma planilha sem cores nem fórmulas: cada linha do arquivo é uma linha da tabela, e as colunas são separadas por vírgula. A primeira linha, quase sempre, traz os nomes das colunas. Quando um valor tem vírgula dentro (como "6,90" ou "Caderno Brochura, 48 folhas"), ele vem entre aspas duplas, para a vírgula de dentro não ser confundida com a que separa colunas.

Qualquer planilha (LibreOffice, Excel, Google Planilhas) salva e abre CSV. É por isso que ele é a "língua franca" entre planilhas e bancos de dados.

A estratégia profissional é sempre a mesma: importar primeiro para uma tabela de passagem (em inglês, staging), do jeito que vier; limpar e conferir lá, com SQL; e só então copiar para a tabela de verdade. A tabela produtos nunca vê a bagunça.

Versão 3: limpar e converter

Cada problema da planilha tem uma função de texto que resolve (aula Funções de Texto). A Ana testa uma de cada vez, no terminal, antes de mudar qualquer coisa. O .nullvalue NULL do começo faz o NULL aparecer escrito na tela, para não ser confundido com um texto vazio:

'[' || nome || ']'
O || junta textos. Os colchetes são um truque para ver espaços, que na tela são invisíveis: [ Borracha Branca ] mostra dois espaços antes e um depois.
TRIM(nome)
Tira os espaços do começo e do fim (do meio, não).
REPLACE(preco, ',', '.')
Troca a vírgula pelo ponto. O resultado ainda é texto: '1.20', com o zero.
CAST(… AS REAL)
Converte o texto em número de verdade: 1.2. Agora as contas funcionam.
NULLIF(estoque, '')
"Se for igual a '', devolva NULL." O texto vazio vira "sem valor", que é o que ele quer dizer (aula O Valor NULL).

Versão 4: as categorias batem?

A tabela produtos não guarda o nome da categoria, e sim o categoria_id. Então cada texto da planilha tem de encontrar a sua categoria na tabela categorias da Aurora. Antes de inserir, a pergunta certa é: alguma não vai encontrar? É o LEFT JOIN … IS NULL de sempre (aula LEFT JOIN):

sqlite> SELECT DISTINCT i.categoria FROM importados i LEFT JOIN categorias c ON c.nome = i.categoria WHERE c.id IS NULL;
┌─────────────────┐
│    categoria    │
├─────────────────┤
│ esporte e lazer │
│ Brinquedo       │
└─────────────────┘

Duas categorias sem par. A "esporte e lazer" é só a caixa das letras: comparando com COLLATE NOCASE, o SQLite ignora maiúsculas e minúsculas, e ela encontra a "Esporte e Lazer". O "Brinquedo" é outro problema: a palavra é diferente, e só um UPDATE na tabela de passagem resolve.

sqlite> SELECT DISTINCT i.categoria FROM importados i LEFT JOIN categorias c ON c.nome = i.categoria COLLATE NOCASE WHERE c.id IS NULL;
┌───────────┐
│ categoria │
├───────────┤
│ Brinquedo │
└───────────┘
sqlite> UPDATE importados SET categoria = 'Brinquedos' WHERE categoria = 'Brinquedo';
sqlite> SELECT changes();
┌───────────┐
│ changes() │
├───────────┤
│ 1         │
└───────────┘

O changes() conta as linhas que o último comando mudou: 1, o Ioiô. Corrigir na tabela de passagem é seguro: o arquivo original continua intacto, e a tabela produtos nem foi tocada.

Formas diferentes de importar

A Ana importou para uma tabela nova, toda TEXT. Outra ideia comum é criar antes uma tabela com tipos e importar direto nela. Veja o que acontece:

sqlite> CREATE TABLE tipada (nome TEXT, categoria TEXT, fornecedor TEXT, preco REAL, estoque INTEGER);
sqlite> .import --csv --skip 1 novos-produtos.csv tipada
sqlite> .mode box
sqlite> .nullvalue NULL
sqlite> SELECT nome, preco, typeof(preco), estoque, typeof(estoque) FROM tipada WHERE rowid IN (1, 4);
┌──────────────────┬───────┬───────────────┬─────────┬─────────────────┐
│       nome       │ preco │ typeof(preco) │ estoque │ typeof(estoque) │
├──────────────────┼───────┼───────────────┼─────────┼─────────────────┤
│ Caneta Gel Preta │ 3,49  │ text          │ 200     │ integer         │
│ Bola de Futebol  │ 59,90 │ text          │         │ text            │
└──────────────────┴───────┴───────────────┴─────────┴─────────────────┘

O --skip 1 pula a linha do cabeçalho (a tabela já tem nomes de coluna). O estoque 200 virou integer: a coluna tipada converte o que parece número. Mas 3,49 não parece, e ficou texto numa coluna REAL; o estoque vazio ficou texto vazio numa coluna INTEGER. O SQLite guarda o que não consegue converter (aula Os Tipos no SQLite). Ou seja: tipos não limpam dados. A limpeza continua sendo com você.

FormaComandoQuando usar

A vírgula decimal que virou número pela metade

Já visto na versão 2, mas é o erro mais caro de todos: '3,49' * 2 dá 6. Se a Ana tivesse inserido os preços sem o REPLACE, a coluna preco teria textos, e cada conta usaria só a parte antes da vírgula. Teste no editor:

       CAST(REPLACE('3,49', ',', '.') AS REAL) * 2 AS limpo,
       typeof('3,49')                            AS tipo;

Como consertar: REPLACE(preco, ',', '.') e CAST(… AS REAL), sempre, antes de levar para a tabela final. E confira o resultado com typeof.

Nos outros bancos

O .import é do programa sqlite3; cada banco tem o seu jeito de ler CSV, e a estratégia da tabela de passagem vale para todos. Trechos ilustrativos, que não rodam no editor:

-- PostgreSQL (no psql, o arquivo é lido do seu computador)
\copy importados FROM 'novos-produtos.csv' WITH (FORMAT csv, HEADER true)

-- MySQL / MariaDB
LOAD DATA LOCAL INFILE 'novos-produtos.csv' INTO TABLE importados
  FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
  IGNORE 1 LINES;

-- SQL Server
BULK INSERT importados FROM 'C:\dados\novos-produtos.csv'
  WITH (FORMAT = 'CSV', FIRSTROW = 2);

Nos três, a tabela de destino precisa existir antes. Mais em As Diferenças entre os Bancos.

Resumo

  • CSV é uma planilha em texto: vírgula separa colunas, aspas protegem as vírgulas de dentro, a primeira linha costuma ser o cabeçalho.
  • Importe com .import --csv para uma tabela de passagem. Numa tabela nova, o cabeçalho vira nome de coluna e tudo vira TEXT; numa tabela existente, use --skip 1.
  • Limpe com SQL: TRIM para espaços, REPLACE(…, ',', '.') + CAST(… AS REAL) para a vírgula decimal, NULLIF(…, '') para células vazias, DISTINCT para linhas repetidas.
  • Confira antes de inserir: typeof para os tipos, LEFT JOIN … IS NULL para nomes sem par, COUNT para as linhas que vão entrar. Um JOIN descarta órfãs em silêncio.
  • Leve para a tabela final com INSERT INTO … SELECT, com PRAGMA foreign_keys = ON no terminal, e apague a tabela de passagem.
  • Exporte com .headers on, .mode csv e .once arquivo.csv; para planilhas em português, .separator ";".
